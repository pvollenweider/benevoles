## Conventions du projet

- **`CHANGELOG.md`** : chaque PR ajoute son entrée dans `[Unreleased]` au moment où elle est faite, y compris une vidéo créée ou régénérée, un ajustement ou une correction d'une fonctionnalité pas encore publiée : on garde la trace de chaque étape, sans réécrire les entrées des PR précédentes. Le nettoyage (fusionner les étapes d'une même fonctionnalité, retirer les corrections de ce qu'aucune version publiée n'a eu, ne garder que les changements réels depuis la dernière version) se fait uniquement au moment de la release, selon la checklist de `CONTRIBUTING.md`. Cette tenue au fil de l'eau évite les trous comme celui de la 1.11.1 (tag et release GitHub existants, mais aucune section CHANGELOG) et le retard de plusieurs versions sur `SECURITY.md`.
- **`GUIDE_ADMIN.md` / `GUIDE_BENEVOLE.md`** : décrivent uniquement l'état actuel du produit, jamais de langage « depuis la version X, c'est comme ça ». Ce sont aussi les sources de `/doc/admin` et `/doc/benevole` (pages publiques rendues depuis ces mêmes fichiers).
- **Release** : suivre la checklist « Publier une nouvelle version » dans `CONTRIBUTING.md` (CHANGELOG, package.json/package-lock.json, SECURITY.md, FONCTIONNALITES.md, guides, tag + release GitHub).
- **`SECURITY.md`** : sa table de versions supportées est vérifiée en CI (`scripts/check-security-md.mjs`) — la mettre à jour dans le même commit que tout bump de `package.json`.
- **Tests unitaires** : toute nouvelle fonctionnalité ou correction de bug doit avoir son test Vitest — au minimum un test de régression pour un bug, plusieurs cas pour une fonctionnalité. Extraire la logique testable dans une fonction pure d'un module `src/lib/*.ts` plutôt que de la laisser inline dans une route ou un composant quand elle mérite un test (voir `gantt-utils.ts`, `pdf-export-gantt.ts`, `sector-leaders.ts` pour le pattern). S'ajoute à la règle déjà en place : toute nouvelle route API admin doit avoir un test d'isolation cross-tenant (`src/__tests__/security/cross-tenant-isolation.test.ts`).
- **Vidéos** : les rendus (`videos/output/**/*.mp4`, `.wav`, `.webm`) ne vont jamais dans Git ; les sources et les petits fichiers (manifestes, scripts, JSON, VTT, TXT, images de preuve citées dans `videos/evidence/`) y vont. Après avoir créé ou régénéré une vidéo (`make video ID=…`), la publier sur `medias.benevol.app` : `make video-publish KUBE_CONTEXT=default ID=…` pour l'aperçu, puis la même commande avec `APPLY=1` (contexte de production : `default`, namespace `benevoles`). La commande compare les empreintes et n'efface jamais rien sur le serveur.
- **Vidéos impactées par un changement** : toute modification de la doc (`GUIDE_ADMIN.md`, `GUIDE_BENEVOLE.md`, `FEATURES.md`) ou de l'interface (libellé, nom de page, parcours, écran) vérifie dans le même travail si des vidéos sont touchées. Chercher le libellé ou la page dans `videos/manifests/*.json` (narration et bloc `viewer`), `videos/scripts/*.md`, les sélecteurs de capture (`videos/tools/record.ts`, `videos/lib/record-*.ts`) et les scénarios `scripts/seed-video-*.ts`. Pour chaque vidéo touchée :
  - mettre à jour le script, la narration du manifeste et le bloc `viewer`, et les sélecteurs de capture dans la même PR que le changement (sinon la prochaine capture échoue) ;
  - si l'image ou la narration ne correspond plus au produit, régénérer la vidéo : capture depuis un checkout à jour de `origin/main` (jamais un checkout en retard), navigateur en français et fuseau `Europe/Zurich`, rien de technique à l'écran, base remise à zéro ; puis `make video ID=…` et `npm run video:validate` ;
  - incrémenter `revision` et mettre à jour `updatedAt` dans `videos/catalog.json`, ajouter une entrée au CHANGELOG, commiter les sources, puis publier les médias comme ci-dessus ;
  - si la régénération n'est pas possible dans le même travail (voix, capture longue), le dire explicitement et noter la vidéo et l'écart dans `videos/FINAL_REVIEW_EVIDENCE.md` ou dans l'issue #644, plutôt que de laisser une vidéo périmée en silence.
